# Telecom Network Anomaly Detection System

An end-to-end ML system that detects anomalies in telecom network KPIs (latency, throughput, packet loss) in real time, deployed as a production-ready REST API.

**Key result (synthetic data, scikit-learn stand-in for XGBoost — see [Results](#results)): on the configured *calibrated* benchmark, median test recall 0.97 / precision 0.91 / F1 0.94 across 10 evaluation seeds (recall above precision, by the owner's choice), vs the original README's 0.952 / 0.769 / 0.851. *Both the level and the final pick are by construction* — the benchmark is as easy as the clean one — so this is not independent evidence the model is good. For a stress test see the `realistic` benchmark: row recall 0.59 / precision 0.50, catching 96% of incidents at ~0.36 false alerts per cell-day.**

---

## Problem

Telecom networks generate thousands of KPI readings per minute across hundreds of cell towers. Identifying fault conditions (congestion, hardware degradation, interference) manually is slow and reactive. This system flags anomalies automatically, enabling NOC teams to react faster.

## Solution

A supervised XGBoost classifier trained on time-series KPI features, served via FastAPI for real-time inference. The pipeline is versioned end-to-end with DVC (data + model artifacts) and MLflow (experiments + model registry).

### KPIs monitored
| KPI | Unit | What it signals |
|---|---|---|
| `latency_ms` | ms | Congestion, backhaul issues |
| `throughput_mbps` | Mbps | Hardware faults, interference |
| `packet_loss_pct` | % | Link instability, interference |
| `sinr_db` | dB | Signal quality, interference |
| `connected_users` | count | Load-related anomalies |

## Quickstart

### 1. Install dependencies
```bash
pip install -r requirements.txt
```

### 2. Run the full pipeline (DVC)
```bash
dvc repro
```
This runs `generate_data.py → features.py → train.py` in order, skipping any stage whose inputs/params haven't changed since the last run. Each `train.py` run also logs to MLflow (see below).

Prefer to run steps manually instead? `make pipeline` (or the individual scripts) works the same way without DVC's caching.

### 3. Inspect experiments
```bash
mlflow ui --port 5000
```
Open [http://localhost:5000](http://localhost:5000) to compare runs, params, and metrics, and to see the model registered under `telecom-anomaly-xgb` in the Model Registry.

**No local machine handy, or just pushed and want to see real numbers without running anything yourself?** Every CI run of `pipeline-and-integration-tests` (`.github/workflows/ci.yml`) trains the real model with real XGBoost and uploads two artifacts:
- `model-artifacts` — `metadata.json` alone has the headline test/validation recall/precision/F1 for that run, no MLflow needed to read it.
- `mlflow-tracking-store` — the actual `./mlruns` directory from that run. Download it from the workflow run's Summary page, then:
  ```bash
  mlflow ui --backend-store-uri ./mlruns
  ```
  This is the first point anywhere real MLflow tracking data for this project exists — nothing in this repo's history has run real `xgboost`+`mlflow` together outside of CI (see `EXPERIMENTS.md` for why: the sandbox this was built in has no network access to install either).

### 4. Start the API
```bash
uvicorn api.main:app --reload --port 8000
```

### 5. Make a prediction

A brand-new cell has no history yet, so the **first call for any `cell_id` intentionally returns 425 Too Early** — the API won't guess with a mostly-empty feature vector:

```bash
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "cell_id": "CELL_001",
    "latency_ms": 145.5,
    "throughput_mbps": 12.3,
    "packet_loss_pct": 8.7,
    "sinr_db": 4.2,
    "connected_users": 87
  }'
```

Send ~20 more readings for the same `cell_id`, in chronological order, and the API starts returning real predictions once it has enough history to compute the time-series features. If you already have pre-computed features on hand, pass them directly via the `features` field instead and skip the warm-up.

### 6. View interactive API docs
Open: [http://localhost:8000/docs](http://localhost:8000/docs)

## Running with Docker

Build and run the full stack — API + Prometheus + Grafana — in containers instead of a local Python environment:

```bash
docker compose up --build
```

The API is then available at [http://localhost:8000](http://localhost:8000) — same endpoints as above. Prometheus, Pushgateway, and Grafana come up alongside it automatically; see [Phase 3](#phase-3--prometheus--grafana) and [Phase 4](#phase-4--evidently-drift-detection) below for their URLs and what's on each dashboard.

Notes:
- Runs as a non-root user, with a container `HEALTHCHECK` against `/health`.
- The trained model artifacts (`models/model.json`, `scaler.pkl`, `metadata.json`) must exist locally before building the image (run `dvc repro` or `dvc pull` first) — they're baked into the image at build time. Rebuild after retraining.
- All three services share a Docker Compose network (`anomaly-net`); Prometheus finds the API via Docker's internal DNS (`anomaly-api:8000`), not `localhost`.

### Phase 1 — MLflow + DVC

**Why both, not just one?**
- **DVC** versions *files* — the raw CSV, the engineered feature set, the trained model binary, the scaler — the same way git versions code, so any commit can be checked out alongside the exact data/model it was trained with (`dvc.lock` pins hashes).
- **MLflow** versions *experiments* — every training run's hyperparameters, metrics, and the resulting model, queryable and comparable, with a registry for promoting a specific run's model to `Staging`/`Production`.

**Configuring a DVC remote** (so `dvc push`/`dvc pull` actually sync artifacts somewhere — without this, DVC only caches locally):
```bash
dvc remote add -d storage s3://your-bucket/telecom-anomaly-dvc
# or: dvc remote add -d storage gs://your-bucket/telecom-anomaly-dvc
dvc push
```

**Configuring MLflow tracking** (defaults to a local `./mlruns` folder if unset — fine for solo experimentation, but point at a real tracking server for team use):
```bash
export MLFLOW_TRACKING_URI=http://your-mlflow-server:5000
```

**Reproducing a specific past state:**
```bash
git checkout <commit>
dvc checkout   # restores data/model files to match that commit's dvc.lock
```

**Real experiment results:** see [`EXPERIMENTS.md`](EXPERIMENTS.md) — read its
**Retractions** section first. Validating this repo end-to-end found that the data generator
was silently non-deterministic (fixed), that `train.py` tuned on its own test set (fixed), and
that the original 95.2% / 76.9% / 0.851 headline came from a test window with only **21
anomalous rows** (recall 20/21, precision 20/26). A follow-up found that even the corrected
benchmark was too clean to say anything about production, so the generator gained a
`realistic` profile (faint faults with gradual onset, noisy labels, benign look-alike surges,
drift) and results are now reported by difficulty level. `scripts/replay_experiments_to_mlflow.py`
loads the sweep into MLflow once it's installed.

### Phase 2 — CI/CD

`.github/workflows/ci.yml` runs on every push/PR to `main`, as four
sequential jobs (each only runs if the previous one passes):

1. **Lint** — `ruff check .`
2. **Unit tests** — `tests/test_features.py` + `tests/test_common.py`.
   These test the pure transformation/split/threshold logic directly, with
   no trained model required, so they run on every PR immediately.
3. **Real pipeline + integration tests** — runs
   `generate_data.py → features.py → train.py` for real (with real
   XGBoost, available in the Actions runner), producing a real trained
   model, then runs `tests/test_api.py` against it, then uploads the
   model artifacts as a workflow artifact.
4. **Docker build & push** — only on a push to `main` (not on PRs). Builds
   the image and pushes to `ghcr.io/<owner>/<repo>:latest` and
   `:<commit-sha>`, authenticated with the Actions-provided
   `GITHUB_TOKEN` — no personal access token is stored or required for
   this workflow.

Run the same checks locally before pushing:
```bash
make lint
make test          # unit tests only, no model needed
make pipeline       # generate_data.py -> features.py -> train.py
make test-api       # needs the above to have run first
```

**Known gap (documented, not hidden):** CI currently runs the three
pipeline scripts directly rather than `dvc repro`, because this repo
doesn't have `dvc init` run yet (no `.dvc/` directory committed — that
needs an actual DVC install to generate, which the environment this repo
was originally built in couldn't do, no network access). Once you run
`dvc init` and commit `.dvc/config` + `.dvc/.gitignore`, swap the
pipeline step in `ci.yml` for `dvc repro` to get caching (skip stages
whose inputs/params haven't changed) instead of a full rerun every time.

```bash

```

Grafana auto-provisions on first boot: the Prometheus datasource and a
9-panel **"Telecom Anomaly Detection API"** dashboard are both already
there, no manual setup. It'll be empty until some traffic hits the API —
generate a batch of realistic + deliberately-anomalous requests to see
it populate:

```bash
make demo-traffic   # or: python scripts/generate_traffic.py --requests 300
```

**What's actually instrumented** (`api/metrics.py`):
- Standard HTTP metrics (request rate, latency percentiles, status codes)
  via `prometheus-fastapi-instrumentator`, labeled by route.
- `anomaly_predictions_total{severity}` — counts by normal/warning/critical.
- `feature_source_total{source}` — precomputed vs live-computed features.
- `anomaly_score` — a histogram of raw model probabilities, so you can see
  the actual score distribution, not just the post-threshold decision.
- `cold_start_responses_total` — how often callers hit the 425
  insufficient-history response.
- `cells_tracked` — gauge, size of the in-process history store.
- `model_threshold_info` — gauge; a step change on this panel marks a
  model redeploy with a newly tuned threshold.

**Deliberately not labeled by `cell_id`** — see the docstring in
`api/metrics.py`. The README describes "hundreds of cell towers" in a
real deployment; a Prometheus label creates one time series per unique
value per metric, so labeling by cell_id would mean hundreds of growing
time series per metric. Severity and feature_source are small, fixed
label sets — safe. Per-cell drill-down belongs in logs, not metrics.

### Phase 4 — Evidently (drift detection)

**Honest disclosure up front:** this was written without network access
to install/verify `evidently` against the real library — its API has had
significant breaking changes across versions. `monitoring/drift_check.py`
pins `evidently==0.4.33` and parses its output defensively: if the
result-dict shape doesn't match what the code expects, it fails loudly
with an actionable error and a raw debug dump, rather than silently
reporting wrong numbers. See that file's module docstring for the full
explanation, and `.github/workflows/ci.yml`'s "Smoke-test the
drift-detection pipeline" step — that's the first real, automatic
validation this code gets, since GitHub Actions has network access this
sandbox didn't.

**What it does:** compares the feature distribution of real production
traffic against the training distribution, using Evidently's
`DataDriftPreset`.

```
data/features.csv (train split)  ──┐
                                    ├─→ Evidently Report → HTML report
logs/inference_log.csv (prod)   ──┘         │
                                             └─→ Pushgateway → Prometheus → Grafana
```

- `api/inference_log.py` — every scored `/predict` request appends its
  full engineered feature vector to `logs/inference_log.csv`
  (best-effort; a logging failure never breaks the actual prediction
  response). This didn't exist before Phase 4 — without it, there was no
  record of what the model actually saw in production to compare against
  training data.
- `monitoring/drift_check.py` — loads the training split as reference,
  the inference log as current, runs Evidently, saves an HTML report to
  `monitoring/reports/`, and pushes a summary to a Prometheus Pushgateway
  (`data_drift_detected`, `data_drift_share`, per-column
  `column_drift_detected{column=...}` — bounded cardinality, ~68 fixed
  feature names, unlike `cell_id`).
- A second Grafana dashboard, **"Data Drift Monitoring"**, auto-provisions
  alongside the Phase 3 one.

Run it:
```bash
docker compose up --build
make demo-traffic        # generates enough logged traffic to compare against
make drift-check         # runs the real check, pushes to Prometheus
```

**Known limitation:** the inference log is a local CSV, appended to by
however many API replicas are running, with no locking beyond a single
in-process `threading.Lock` (documented in `inference_log.py`) — fine for
one instance, not safe for multiple replicas writing concurrently. A real
multi-replica deployment would ship these rows to a proper sink (Kafka,
a feature store, cloud logging) instead.

### Phase 5 — Airflow

**Same honesty pattern as Phase 4:** Airflow isn't installable in the
sandbox this was built in either, so the DAG's exact runtime behavior is
unverified against a live scheduler — though confidence is higher than
Evidently's case, since the TaskFlow API (`@dag`/`@task`) has been stable
for years. `.github/workflows/ci.yml`'s `airflow-dag-validation` job
actually installs real Airflow and parses this DAG with a real `DagBag`,
asserting the exact task set — that's the first genuine verification
this graph gets, and it's worth checking that job's result before
trusting anything below.

**What it does:** `airflow/dags/telecom_anomaly_pipeline.py`, scheduled
`@daily`:

```
run_drift_check
      │
      ▼
decide_whether_to_retrain (branch)
   │                   │
[drift]            [no drift]
   ▼                   ▼
generate_data      skip_retrain
   ▼
engineer_features
   ▼
train_model
   ▼
promote_model   (re-checks the recall floor independently —
                 "drift happened" and "new model is good enough
                 to serve" are two separate gates)
```

Only retrains when `monitoring/drift_check.py` (Phase 4, unchanged, just
invoked as a task) actually detects drift — not on every scheduled tick
regardless. `models/promote.py` holds the promotion decision as a pure,
independently-unit-tested function (`should_promote`, 5 tests, all
actually executed and passing here) separated from the MLflow
registry I/O around it.

Run it (needs the Phase 3 stack's network to exist first):
```bash
docker compose up --build              # anomaly-net + api + prometheus + grafana + pushgateway
make airflow-init                       # one-time: create the Airflow metadata DB + admin user
make airflow-up                         # webserver + scheduler, joins the same network
```
Open [http://localhost:8080](http://localhost:8080) (login `admin` / `admin` — same "change this off your laptop" caveat as Grafana).

**Two things documented as real gaps, not silently glossed over:**
- `generate_data` is deterministic (fixed seed; enforced by
  `tests/test_generate_data.py`) — rerunning it produces byte-identical data. In this demo it stands in for "new production
  data arrived"; a real deployment would pull from wherever labeled
  production data actually lands instead of a synthetic generator.
- **The DAG branches on Evidently's dataset-level flag, which may be too
  coarse here.** As I understand Evidently's default, `dataset_drift` is
  only true when at least 50% of columns drift. This model has 68 features
  derived from just 5 KPIs. In an offline check (per-feature KS tests
  standing in for Evidently, so indicative only), shifting two of the five
  KPIs substantially (latency +30, throughput ×0.6) drifted 20 of 68
  features (29%) — enough to matter, not enough to trip a 50% flag. If
  that holds with real Evidently, consider branching on `drift_share` with
  a lower threshold (or per-KPI) instead; retraining is already gated by
  `models/promote.py`, so a lower trigger is cheap. Not changed here
  because it can't be validated without the real library.
- Promoting a model to "Production" in the MLflow registry currently has
  **no effect** on what `api/main.py` actually serves — it always loads
  `models/model.json` directly off disk. Wiring the API to load from
  (and reload on promotion from) the registry is real future work.

### Phase 6 — ONNX + Triton

**Read this before reaching for this phase.** Triton Inference Server is
built for GPU-bound deep learning workloads at real scale — batching
requests across many concurrent clients, serving large neural networks,
squeezing out throughput that matters when you're paying for GPU time.
This project's model is a single small XGBoost classifier that already
predicts in under a millisecond natively (see the README's own "Why
XGBoost?" section above). Converting it to ONNX and serving it through
Triton **works**, and this phase does exactly that — but for a model
this size, embedding ONNX Runtime directly inside FastAPI would give
nearly identical latency with a small fraction of the operational
overhead (no separate container, no protocol translation, no second
model-repository directory to keep in sync). This phase exists to
demonstrate the pattern, not because this specific model needed it.
If you're deciding whether to bring this into a real project of your
own: ask whether you actually have the GPU-scale serving problem Triton
solves, not whether the tooling is impressive.

**Same honesty pattern as Phases 4 and 5:** `onnxmltools`/`onnxruntime`
aren't installable in the sandbox this was built in, so the conversion
API is unverified against the real libraries. Unlike Evidently, though,
this script doesn't just parse defensively and hope — it **re-scores
real held-out data through both the native and converted models and
refuses to write `model.onnx` at all if they disagree** beyond a tight
tolerance (`models/convert_to_onnx.py`, `PROB_ATOL = 1e-4`). CI's
"Convert to ONNX + validate parity" step is where this actually runs
against the real libraries for the first time.

**What it does:**
```
models/model.json (native XGBoost)
        │
        ▼  models/convert_to_onnx.py  (converts, then validates parity
        │                              against real held-out data before
        │                              accepting the result)
models/model.onnx
        │
        ▼  make triton-prep  (copies into place)
triton_model_repository/telecom_anomaly_xgb/1/model.onnx
        │
        ▼  Triton (ONNX Runtime backend)
        │
        ▼  scripts/query_triton.py  (real KServe v2 HTTP request,
                                      cross-checked against /predict
                                      for the same row)
```

Run it:
```bash
docker compose up --build                          # anomaly-net must exist first
make triton-up                                       # converts, validates, copies, starts Triton
make query-triton                                     # sends one real row, compares vs /predict
```

Triton's Prometheus metrics (request count, latency, queue time) are
scraped automatically by `prometheus/prometheus.yml`'s `triton` job —
absent from Prometheus's target list when this stack isn't running,
not an error.

**Real, compounding gap worth naming plainly:** `requirements.txt` is
now one file shared by the API image, CI, and every pipeline script —
meaning the API's Docker image installs `evidently`, `mlflow`, `dvc`,
`onnxruntime`, and friends despite never importing any of them at
runtime. This was a reasonable simplification in Phase 1 and has quietly
compounded ever since; a leaner production image would split this into
`requirements-api.txt` (what `api/main.py` actually imports) versus
`requirements-pipeline.txt` (everything else), and point the Dockerfile
at only the former. Not done here — flagging it rather than leaving it
silently implied-fine.

### Phase 7 — Kubernetes

Manifests in [`k8s/`](k8s/README.md) (kustomize): the API on 2+ replicas with an autoscaler, a **Redis** that holds the shared
per-cell history and inference log, Prometheus + Pushgateway + Grafana (both dashboards provisioned), and an hourly
drift-check CronJob. Pods run non-root with a read-only root filesystem.

```bash
GRAFANA_PASSWORD='<choose>' make k8s-secret && make k8s-apply     # then: make k8s-port-forward / make k8s-grafana
```

**What changed in the code:** `REDIS_URL` moves per-cell history and the inference log from process memory/a local CSV into
Redis (`api/shared_store.py`); unset, nothing changes. This is what lets replicas share state: previously a second replica
would see only part of a cell's readings and answer `425` forever. A Redis outage returns `503` for raw readings only.

**Bugs found while validating** (both fixed, with regression tests): (1) a cell whose readings mix client-supplied timestamps
(`...Z`) with server-assigned ones (microseconds) crashed feature computation; (2) the API tests posted perfectly constant KPIs,
whose z-score is undefined, so a warm-up test could not pass on current pandas.

**Verified here vs. not** — in the sandbox: all manifests render and pass `kubeconform --strict`; the Redis code runs against a
live Redis; two real API processes sharing it, with real Prometheus and Pushgateway, pass the shared-history, dashboard-query,
drift-metrics and Redis-outage checks (model and Evidently are stand-ins there). **Not run anywhere yet:** an actual cluster —
the CI job `kubernetes-manifests` (`scripts/k8s_e2e.sh` on kind, with real XGBoost and Evidently) is the first real check.
Resource limits are unmeasured guesses. Airflow and Triton are not ported. Details and limits: [`k8s/README.md`](k8s/README.md).

## Feature Engineering

For each KPI, the following features are computed per cell tower:

| Feature type | Detail |
|---|---|
| **Lag features** | Values at t-1, t-2, t-4, t-8 (15 min to 2 hours ago) |
| **Rolling mean** | 1h and 4h windows |
| **Rolling std** | 1h and 4h windows — captures variance bursts |
| **Rolling min/max** | 1h window |
| **Z-score** | Deviation from 4h rolling mean |
| **Rate of change** | `(t - t-1) / t-1` — detects sudden jumps |
| **Time features** | Hour of day, day of week, is_weekend |

Total: **68 features** across 5 KPIs.

| Feature group | Count |
|---|---|
| Lag features (t-1, t-2, t-4, t-8) | 5 KPIs × 4 = 20 |
| Rolling mean (1h, 4h) | 5 KPIs × 2 = 10 |
| Rolling std (1h, 4h) | 5 KPIs × 2 = 10 |
| Rolling min/max (1h) | 5 KPIs × 2 = 10 |
| Z-score (4h window) | 5 KPIs × 1 = 5 |
| Rate of change | 5 KPIs × 1 = 5 |
| Raw KPI values | 5 |
| Time features (hour, day_of_week, is_weekend) | 3 |
| **Total** | **68** |

## Model Details

| Parameter | Value |
|---|---|
| Algorithm | XGBoost (gradient boosted trees) |
| Trees | 300 (with early stopping) |
| Max depth | 6 |
| Learning rate | 0.05 |
| Class imbalance | Handled via `scale_pos_weight` |
| Threshold | Highest threshold reaching `threshold.validation_recall_target` (0.975) **on the validation slice** (never on the test set); chosen per benchmark profile (F2 rule on development seeds, or the owner's pick from the calibration table for `calibrated`). `min_recall` (0.93) is the separate promotion gate on test recall |
| Split | Chronological, no shuffle: 64% train / 16% validation / 20% test (`split.train_ratio`, `split.val_fraction`) |

All of the above now live in `params.yaml`, not hardcoded in `train.py` — change a value there and `dvc repro` knows to retrain.

### Why XGBoost?
- Handles tabular time-series features well out of the box
- Robust to feature scale differences and missing values
- Fast inference (<1ms per prediction) — suitable for real-time monitoring
- Feature importance scores aid explainability for NOC teams

### Why tune the threshold?
The default 0.5 threshold maximizes accuracy, not recall. In anomaly detection, a missed fault (false negative) is far more costly than a false alarm. Threshold tuning lets us control this trade-off explicitly.

Original README, for comparison: recall 0.952, precision 0.769, F1 0.851 — one 21-row test window.

- **Calibrated (configured default).** The benchmark's difficulty was explored against the original's recall/precision/F1 on *development* seeds; the final setting (abrupt faults, `ramp_fraction` 0.0, operating point 0.975) was **picked by the project owner** so recall sits above precision. The pre-stated distance rule would have picked ramp 0.1 / 0.95 (0.94 / 0.84 / 0.89 on eval seeds). Ramp 0.0 is clean-level difficulty, so this is an easy, upper-bound benchmark: it shows the pipeline works, not that the model is good. Per-seed spread is wide (precision 0.69–0.98), so the original's single 0.769 was one draw.
- **Clean** is an upper bound (abrupt step-change faults, perfect labels): recall matches but precision/F1 overshoot.
- **Realistic** is the more honest stress test (faint faults, noisy labels, benign surges, drift). An ablation in
  EXPERIMENTS.md shows nearly all of its drop comes from faint, gradually-starting faults and imperfect labels.
- **Not calibrated to any real network** (none was available), and none of these is a production forecast. If someone asks how
  it compares to the original project, say the benchmark was calibrated to it and the final pick was the owner's; if they ask whether the model is good, don't answer with these numbers.
- **Row vs incident metrics.** Row-level recall treats every 15-minute interval independently; operations teams think in incidents.
  `models/alerting.py` scores incident detection, false alerts per cell-day and detection delay.

### Switching benchmark

Set `data.profile` (`legacy` = clean, `calibrated`, `realistic`) **and** `threshold.validation_recall_target`
(clean → 0.96, calibrated → 0.975, realistic → 0.5) in `params.yaml`, then
`python data/generate_data.py && python data/features.py`. A test fails if only one of the two is changed. Event metadata goes in
`data/events.csv`, never in `raw_kpis.csv`, so it can't leak in as a feature.

### What this means for promotion

`min_recall: 0.93` (the test-recall floor `models/promote.py` requires) is met by 10/10 evaluation seeds on the calibrated
benchmark, 8/10 on clean, but **0/10 on realistic** — where forcing a 0.96 validation target means flagging about
85% of all rows at 2% precision. I did not lower the floor — it reads as a business requirement. On realistic data your options:
accept it, set a floor the data can support, or gate on incident-level detection plus a false-alert budget (see EXPERIMENTS.md).
